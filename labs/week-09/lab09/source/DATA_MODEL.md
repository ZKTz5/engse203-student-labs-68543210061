## 2. ทำไมต้องแยกเป็น 2 ตาราง

### ปัญหามีออะไรบ้าง
1.ข้อมูลซ้ำซ้อน
หากสมชายส่งคำร้อง 10 รายการ ชื่อ "สมชาย ใจดี" จะถูกเก็บซ้ำ 10 ครั้ง ทำให้ใช้พื้นที่จัดเก็บมากขึ้นโดยไม่จำเป็น

2.แก้ไขข้อมูลไม่ครบ
หากสมชายเปลี่ยนชื่อเป็น "สมชาย วัฒนากุล" จะต้องแก้ไขทุกคำร้องที่เคยสร้างไว้
ตัวอย่างเช่น หากมีคำร้อง 10 รายการ ก็ต้องแก้ 10 จุด
หากลืมแก้เพียงบางรายการ จะทำให้ในระบบมีทั้งชื่อเก่าและชื่อใหม่ปะปนกัน ส่งผลให้ข้อมูลไม่ถูกต้อง

3.พิมพ์ผิดแล้วไม่มีใครรู้
ผู้ใช้คนเดียวกันอาจถูกบันทึกชื่อแตกต่างกัน เช่น
```
สมชาย ใจดี
สมชาย ใจดึ
สมชาน ใจดี
```

### การแยกตารางช่วยแก้ปัญหาอย่างไร
- ข้อมูลผู้ใช้อยู่ในตาราง users
- ข้อมูลคำร้องอยู่ในตาราง requests
- ตาราง requests เก็บเพียง requester_id เพื่ออ้างอิงไปยังผู้ใช้
ดังนั้นหากสมชายเปลี่ยนชื่อ จะต้องแก้ไขเพียง 1 จุดในตาราง users เท่านั้น

## 3. รายละเอียดตาราง

### ตาราง `users`
 
| คอลัมน์ | ชนิดข้อมูล | ข้อกำหนด | เหตุผล |
|----------|----------|----------|----------|
| id | INTEGER | PRIMARY KEY, AUTOINCREMENT | ใช้เป็นรหัสประจำตัวผู้ใช้ โดยระบบจะสร้างเลขให้เองและไม่ซ้ำกัน |
| name | TEXT | NOT NULL | ผู้ใช้ทุกคนต้องมีชื่อ เพื่อให้ทราบว่าเป็นใคร |
| department | TEXT | NOT NULL | ใช้ระบุภาควิชาของผู้ใช้ เพื่อช่วยในการค้นหาและจัดกลุ่มข้อมูล |
| email | TEXT | NOT NULL, UNIQUE | ใช้ติดต่อผู้ใช้ และป้องกันการใช้อีเมลซ้ำกัน |
 
### ตาราง `requests`
 
| คอลัมน์ | ชนิดข้อมูล | ข้อกำหนด | เหตุผล |
|----------|----------|----------|----------|
| id | TEXT | PRIMARY KEY | ใช้เก็บรหัสคำร้อง เช่น REQ-001 ทำให้จดจำและอ้างอิงได้ง่าย |
| requester_id | INTEGER | NOT NULL, FOREIGN KEY | ใช้เชื่อมคำร้องกับผู้ใช้ในตาราง users และช่วยลดข้อมูลซ้ำซ้อน |
| request_type | TEXT | NOT NULL, CHECK | จำกัดประเภทคำร้องให้เป็นค่าที่กำหนดไว้เท่านั้น |
| location | TEXT | NOT NULL | ใช้ระบุสถานที่ที่เกิดปัญหาหรือสถานที่ที่เกี่ยวข้อง |
| details | TEXT | NOT NULL | ใช้อธิบายรายละเอียดของปัญหาหรือคำร้อง |
| priority | TEXT | NOT NULL, DEFAULT 'normal', CHECK | กำหนดระดับความสำคัญของคำร้อง และป้องกันการกรอกค่าที่ไม่ถูกต้อง |
| status | TEXT | NOT NULL, DEFAULT 'pending', CHECK | ใช้ติดตามสถานะของคำร้อง และจำกัดให้ใช้เฉพาะสถานะที่ระบบรองรับ |
| created_at | TEXT | NOT NULL, DEFAULT datetime(...) | บันทึกวันและเวลาที่สร้างคำร้องโดยอัตโนมัติ เพื่อใช้ติดตามและเรียงลำดับข้อมูล |

## 4. เหตุผลของการเลือกชนิดและข้อกำหนด

1.สำหรับตาราง users ใช้ INTEGER เพราะเป็นแค่เลขประจำตัวผู้ใช้ที่เอาไว้แยกแต่ละคนออกจากกัน เช่น 1, 2, 3, 4 ทำให้จัดการและเชื่อมข้อมูลได้ง่าย
ส่วนตาราง requests ใช้ TEXT เพราะต้องการให้รหัสคำร้องอ่านเข้าใจง่าย

2.ถึง API จะตรวจข้อมูลก่อนบันทึกได้ แต่ถ้ามีคนแก้ข้อมูลผ่าน SQL โดยตรง หรือเกิดข้อผิดพลาดใน API ข้อมูลที่ไม่ถูกต้องก็อาจถูกบันทึกเข้าไปได้

## 5. ตัวอย่างการใช้ JOIN

ตัวอย่างการดึงข้อมูลคำร้องพร้อมชื่อผู้แจ้ง โดยใช้การเชื่อมข้อมูลระหว่างตาราง `requests` และ `users`
 
### SQL
 
```sql
SELECT r.id, u.name, r.status FROM requests r
JOIN users u ON u.id = r.requester_id
ORDER BY r.id;
```
 
### ผลลัพธ์
 
| id | name | status |
|------|------|------|
| REQ-001 | สมชาย ใจดี | pending |
| REQ-002 | สมหญิง แสนดี | completed |
| REQ-003 | สมปอง รักเรียน | in-progress |
 
### อธิบาย
 
คำสั่ง `JOIN` ใช้เชื่อมข้อมูลระหว่างตาราง `requests` และ `users` ผ่านคอลัมน์ `requester_id` ที่อ้างอิงไปยัง `users.id` ทำให้สามารถแสดงชื่อผู้แจ้งพร้อมข้อมูลคำร้องได้ โดยไม่ต้องเก็บชื่อผู้ใช้ซ้ำในทุกคำร้อง

## 6. ข้อสังเกตสำหรับสัปดาห์ที่ 10

จากการใช้ JOIN พบว่าสามารถรวมข้อมูลจากหลายตารางให้ออกมาเป็นข้อมูลรูปแบบเดียวกับที่ React ใช้งานได้

ดังนั้น แม้ข้อมูลในฐานข้อมูลจะถูกแยกเก็บเป็นตาราง users และ requests แต่เมื่อใช้ JOIN แล้ว ผลลัพธ์ที่ได้ก็ยังเหมือนกับข้อมูล JSON ที่ส่งให้ React ทำให้สามารถเปลี่ยนจากการเก็บข้อมูลแบบ JSON มาใช้ SQLite ได้โดยไม่ต้องเปลี่ยนรูปแบบข้อมูลที่ส่งไปยัง Frontend

## ผลการทดสอบ Constraint

### ① Foreign Key

**คำสั่งที่ลอง**

```sql
INSERT INTO requests (id, requester_id, request_type, location, details)
VALUES ('REQ-TEST', 99999, 'แจ้งซ่อม', 'ห้องทดสอบ', 'ทดสอบระบบ');
```

**ผลที่ได้** `FOREIGN KEY constraint failed` ✓ ถูกปฏิเสธตามที่ควร

---

### ② CHECK

**คำสั่งที่ลอง**

```sql
INSERT INTO requests (id, requester_id, request_type, location, details, status)
VALUES ('REQ-TEST', 1, 'แจ้งซ่อม', 'ห้องทดสอบ', 'ทดสอบระบบ', 'ยกเลิก');
```

**ผลที่ได้** `CHECK constraint failed: status IN ('pending','in-progress','completed')` ✓ ถูกปฏิเสธตามที่ควร

---

### ③ UNIQUE (user.email)

**คำสั่งที่ลอง**

```sql
INSERT INTO users (name, department, email)
VALUES ('ทดสอบระบบ', 'วิศวกรรมซอฟต์แวร์', 'somchai@rmutl.ac.th');
```

**ผลที่ได้** `UNIQUE constraint failed: users.email` ✓ ถูกปฏิเสธตามที่ควร

---

### ④ UNIQUE (requests.id)

**คำสั่งที่ลอง**

```sql
INSERT INTO requests (id, requester_id, request_type, location, details)
VALUES ('REQ-001', 1, 'แจ้งซ่อม', 'ห้องทดสอบ', 'ทดสอบระบบ');
```

**ผลที่ได้** `UNIQUE constraint failed: requests.id` ✓ ถูกปฏิเสธตามที่ควร

---

### ⑤ NOT NULL (location)

**คำสั่งที่ลอง**

```sql
INSERT INTO requests (id, requester_id, request_type, details)
```

**ผลที่ได้** `NOT NULL constraint failed: requests.location` ✓ ถูกปฏิเสธตามที่ควร
